For exchanges

List CMFD the way you list Bitcoin.

Run cmfd-node exchange-wallet on your own server and point your existing Bitcoin integration at it. It answers Bitcoin Core's wallet RPC (getnewaddress, listsinceblock, sendtoaddress and the rest), keeps your keys with you, and reads the chain from our hosted endpoint, so you never download the chain.

Setup

You need a Linux or Windows server, the hosted-endpoint credential Common Foundry issues to your exchange, and about ten minutes.

  1. Download and verify the release

    Get the runtime archive for your platform from the v1.0.10 release, together with SHA256SUMS.txt, SHA256SUMS.txt.sig and MAINNET-RELEASE.allowed_signers. Check the signature, then the archive.

    shell
    ssh-keygen -Y verify -f MAINNET-RELEASE.allowed_signers \
  -I commonfoundry-mainnet-owner -n commonfoundry-release \
  -s SHA256SUMS.txt.sig < SHA256SUMS.txt
sha256sum --ignore-missing -c SHA256SUMS.txt
tar -xzf commonfoundry-mainnet-runtime-linux-x86_64-v1.0.10.tar.gz

    The signing key is SHA256:cA1Tsf8hL/pxDV5WpOE3iPW3b4uDQosu1dOh//4a/fk. The wallet is part of cmfd-node in that archive; Windows uses the .zip runtime and cmfd-node.exe.

  2. Write the settings file

    Create a directory for the wallet and put cmfd-wallet.conf in it. The format is the familiar bitcoin.conf style.

    /var/lib/cmfd-wallet/cmfd-wallet.conf
    # Your integration logs in to the wallet with these (HTTP Basic).
rpcuser=exchange
rpcpassword=<at least 16 random characters>
# Default: listen on 127.0.0.1:39120. To accept another host, set
# rpcbind and list every allowed address or network with rpcallowip.
#rpcbind=10.0.0.5
#rpcport=39120
#rpcallowip=10.0.0.0/8
# Where the wallet reads the chain.
upstream=https://sg-rpc.commonfoundry.ai/mainnet
upstreamuser=<your hosted-endpoint user>
upstreampassword=<your hosted-endpoint password>

  3. Start the wallet and back it up

    On first start the wallet creates wallet.json, which holds your keys. Back it up straight away. Every address the wallet will ever hand out derives from that one file, so you never need a new backup after getnewaddress.

    shell
    ./cmfd-node exchange-wallet --wallet-dir /var/lib/cmfd-wallet

    To run it as a service, a systemd unit like this works. The wallet saves its state when it receives the stop signal.

    /etc/systemd/system/cmfd-wallet.service
    [Unit]
Description=Common Foundry exchange wallet
After=network-online.target
Wants=network-online.target

[Service]
User=cmfd
ExecStart=/opt/cmfd/cmfd-node exchange-wallet --wallet-dir /var/lib/cmfd-wallet
Restart=on-failure

[Install]
WantedBy=multi-user.target

  4. Point your Bitcoin integration at it

    Use host 127.0.0.1, port 39120 and the rpcuser / rpcpassword from step 2 in whatever Bitcoin client library or adapter you already run. bitcoin-cli works too:

    shell
    bitcoin-cli -rpcport=39120 -rpcuser=exchange -rpcpassword=… getblockchaininfo
bitcoin-cli -rpcport=39120 -rpcuser=exchange -rpcpassword=… encryptwallet "<passphrase>"
bitcoin-cli -rpcport=39120 -rpcuser=exchange -rpcpassword=… backupwallet /secure/cmfd-wallet.json

    Encrypt before the wallet holds funds, then back up again: a backup taken before encryption still holds the unencrypted key.

Deposits

Give each customer an address with getnewaddress "user-123". The label is yours to use for your own reference. Then follow incoming payments the same way you do with bitcoind:

bitcoin-cli … listsinceblock "<lastblock>" 60
{
  "transactions": [
    {
      "address": "9f0c5e…e41a",
      "category": "receive",
      "amount": 12.34567890,
      "label": "user-123",
      "vout": 0,
      "confirmations": 60,
      "blockhash": "4b1d0e…77c2",
      "blockheight": 3912,
      "txid": "a7e310…0c95",
      "time": 1791249601
    }
  ],
  "removed": [],
  "lastblock": "c03f18…9a40"
}
  • Credit a deposit once confirmations reaches 60. Passing 60 as the second argument keeps a transaction in every reply until it gets there.
  • Store lastblock and pass it to the next call.
  • Entries in removed were dropped by a chain reorganization. Reverse any credit you gave for them.
  • Deposits appear once they are in a block (1 confirmation), not while they wait in the mempool.
  • Mined coins paid straight to a deposit address show as immature until they are 100 blocks deep, then as generate.

gettransaction, getreceivedbyaddress, listreceivedbyaddress and listtransactions work as you expect if your system uses them instead.

Withdrawals

shell
bitcoin-cli … walletpassphrase "<passphrase>" 60
bitcoin-cli … sendtoaddress "<customer address>" 25.5 "withdrawal 8812"
bitcoin-cli … gettransaction "<txid>"
  • Amounts take up to eight decimals. The 0.1 CMFD fee comes out of the wallet, or out of the payment when you set subtractfeefromamount.
  • sendmany pays up to 127 recipients in one transaction.
  • The wallet records each payment before broadcasting it. If the endpoint cannot confirm the broadcast, sendtoaddress still returns the txid and the wallet keeps rebroadcasting until the payment is mined.

Never send a withdrawal twice. If your call times out, look the payment up with gettransaction or listtransactions before trying again, exactly as you would with bitcoind.

This chain cannot spend an output until it is mined, so change from a payment returns after the next block, about a minute. The wallet splits change to keep at least 25 coins ready, which lets it make many withdrawals per block. If every coin is waiting, sendtoaddress returns error -6 and says to retry after the next block.

Differences from Bitcoin Core

These are the only places where your Bitcoin integration needs a setting or a second look.

Addresses
64 lowercase hex characters (an x-only public key) with no checksum. Check every customer withdrawal address with validateaddress, and have customers paste rather than type it; see Checking addresses.
Fees
Every transaction pays the network minimum of 0.1 CMFD, which is burned. settxfee, fee_rate and conf_target are accepted and ignored; estimatesmartfee returns 0.1.
Change
Unconfirmed outputs cannot be spent, so change returns after one block. The wallet keeps 25 coins ready to cover this.
Incoming
Deposits appear once mined (1 confirmation), not while in the mempool.
Input limit
A transaction takes at most 128 inputs. When the wallet holds more than 200 coins, it merges the 128 smallest into one and pays the 0.1 CMFD fee for it. Merges are not listed by listtransactions; gettransaction shows them. Set consolidatethreshold=0 to turn this off.
Not available
Raw-transaction building (createrawtransaction, signrawtransactionwithwallet, fundrawtransaction), key import and export, message signing, and multiple wallets.

Checking addresses

Addresses carry no checksum. A valid address is 64 lowercase hex characters whose value is the x-coordinate of a point on the secp256k1 curve. That rule rejects malformed input and about half of all mistyped addresses, but the other half still form valid keys. Have customers paste or scan their withdrawal address rather than type it, and show it back to them before you send. Try the rule here; it runs in your browser and sends nothing anywhere.

The example is the secp256k1 generator point, a valid key that nobody should pay. Your integration should still call validateaddress on the wallet, which applies the same rule.

Security and operations

Keys and backups

  • wallet.json holds the master key (encrypted once you call encryptwallet), the address counters and labels. Back it up after creating and after encrypting the wallet.
  • Run one wallet process per wallet.json. Two copies spending from the same keys would compete for the same coins.
  • The RPC listens on 127.0.0.1 by default. Opening it to another host requires rpcbind plus rpcallowip; keep it on a private network.

Monitoring

  • getblockchaininfo reports blocks (the wallet's height) and headers (the endpoint's); they should match within a block.
  • getconnectioncount is 1 while the endpoint answers. warnings explains any problem.
  • The wallet keeps answering while the endpoint is unreachable and catches up when it returns. Logs are in <wallet-dir>/logs.

Restore

Put wallet.json and cmfd-wallet.conf in an empty directory and start the wallet. It rescans from the block at which the wallet was created, about four blocks per second from the hosted endpoint, and finds every address, including ones handed out after the backup was made.

Hosted endpoint

Common Foundry runs the mainnet endpoint the wallet reads from, so you do not store the chain. Each exchange gets its own credential, delivered privately.

Prefer your own infrastructure? Run a full node with cmfd-node run --exchange-rpc-bind 127.0.0.1:<port> --exchange-rpc-auth-file <file> and set upstream=http://127.0.0.1:<port>. Plain http:// is accepted only for this machine. A full node stores the chain, which grows by roughly 12 GB a day.

Advanced route

Some exchanges prefer to hold one key file per address and build every transaction themselves. For that, the release includes offline tools (exchange-key-new, exchange-tx-sign) and the exchange JSON-RPC with deposit event streams. The full integration guide covers this route in detail, along with error catalogs and the hosted endpoint's method list.
