# Common Foundry v0.1.0-devnet.14

Devnet-14 RC1 is a private testing candidate that combines the persistent peer
and multi-vendor miner work from the unpublished Devnet-12/13 candidates with
the latest ForgeMatrix production-proof research. It remains on the existing
Devnet-0 chain. The production proof profile is still disabled.

## Changes

### Wallet networking and diagnostics

- Added a persistent peer manager to the desktop wallet. Testers can add,
  remove, and reset outbound peers from the Network screen.
- Numeric peer addresses default to TCP port `18444`; validated settings are
  applied immediately and restored after restart.
- Retained structured node logging and clearer startup diagnostics while
  keeping wallet RPC local to the computer.

### Standalone mining

- Retained CUDA targets for Volta and NVIDIA RTX 20-, 30-, 40-, and 50-series
  GPUs, plus the `compute_70` PTX fallback.
- Retained deeper CUDA scheduling and explicit multi-GPU throughput controls.
- Included the runtime-loaded OpenCL backend for Intel Arc, with device
  enumeration and explicit backend selection.
- Windows and Linux packages include editable launchers and use the connected
  node's block template instead of maintaining a second blockchain.

### Dependency security

- Updated `time` to 0.3.47 and the locked Tauri `plist`/`quick-xml` chain to
  `plist` 1.10.0 and `quick-xml` 0.41.0, removing versions affected by RustSec
  denial-of-service advisories `RUSTSEC-2026-0009`, `RUSTSEC-2026-0194`, and
  `RUSTSEC-2026-0195`.

### Release identity guards

- Native CUDA and OpenCL builders now write identity-only build receipts from
  the same invocation that built and inspected each library. Packaging rejects
  missing, changed, wrong-source, wrong-script, wrong-target, and wrong-commit
  receipts.
- Windows and Linux release builders require an externally supplied full
  candidate commit. Linux packaging also checks Linux, x86-64, glibc, the Rust
  host target, and ELF class, machine, and type.
- ZIP and tar creation reject symbolic links, unsafe member names, special
  files, and noncanonical member types and metadata. Final release metadata is
  constrained by a tracked Devnet-14 asset inventory.
- Linux CUDA builds strip nonessential host symbols before architecture,
  differential, and receipt checks. This removes nvcc process-specific
  temporary symbols so independent builds from the same inputs and recorded
  toolchain produce the same shipped library bytes.
- Linux `.deb` output is normalized to the release commit timestamp, root
  ownership, and uniform gzip compression, then rebuilt a second time and
  accepted only if both normalized packages are byte-identical.
- A build receipt is not authenticated provenance. Release download trust still
  requires an independently verified final checksum file bound to a signed
  release tag; these guards do not replace that signature or an independent
  reproducible-build comparison.

### Production-proof research

- Closed the raw Layout V5 composition interface. The prover now consumes an
  opaque verified execution capability and derives the setup, block challenge,
  final activation, output digest, and work digest internally.
- Added a provider-owned atomic path from verified ForgeMatrix execution through
  Layout V5 and the native BLAKE3 opening. Callers cannot substitute raw bridge
  fields or independently mix proof components.
- Added a dormant authenticated Layout V5 candidate seal and verifier using the
  existing canonical `CFV3CP02` envelope. Only the provider-owned opaque
  execution capability can be sealed; Record V2, setup, network, challenge,
  work, target, and the V5 proof context are revalidated before acceptance.
- Layout V5 decoding is fail-closed with exact end-of-frame checks and no V4
  retry or downgrade path. Behavioral tests cover successful bounded sealing
  and record, setup, block, context, challenge, work, target, trailing-byte,
  and V4-substitution failures.
- Production preflight requires the pinned n=33 geometry, the ordered 128
  structured claims, and the six statement-owned native BLAKE3 claims before
  expensive proving begins.
- Added bounded adversarial tests for block, setup, activation, output-digest,
  work-digest, claim-order, provenance, and scratch-cleanup failures.
- Added a dormant, feature-gated keyless Type-6 final-receipt pipeline. A strict
  paths-only plan routes the independently anchored Type-5 prefix, ordered
  contributions and reproducer reports, shared candidate artifacts, and the
  exact Independent `CMFDIL01` subset through the retained validators. Path
  claims alone confer no authority.
- Type-6 preparation derives every receipt field and the public signing message
  from validated capabilities. Staging revalidates the inputs from disk,
  requires the exact ordered `N + R` external BIP340 signatures, creates and
  canonically reopens the record, then reauthenticates the plan and Type-5
  prefix before the final bank-last guard. The commands expose no private-key
  option and do not sign, publish, mirror, or activate anything.
- Added independently anchored Completed-transcript staging from one exact
  Type-5 prefix and one canonical signed Type-6 record. It verifies the explicit
  ceremony ID, complete sequence, and full-roster signatures, retains and
  reauthenticates both inputs through output confirmation, and reports
  publication as pending. This stage validates the signed wire record and
  retained inputs only; it does not freshly validate the external candidate,
  `CMFDRP01`, or `CMFDIL01` artifacts.

## Compatibility and upgrade notes

- Devnet-14 keeps the current Devnet-0 chain, P2P protocol, wallet data format,
  and TCP port `18444`.
- Existing wallet data should be preserved. Replace the application binaries;
  do not delete the wallet data directory.
- Production proof tag 3 remains unavailable to consensus. Devnet blocks still
  use the small reference relation and its existing proof tag.
- The new ceremony commands are offline, feature-gated tooling and do not
  change Devnet block validation, wallet data, P2P behavior, or mining. On
  Unix, Type-6 preparation and staging require a soft `RLIMIT_NOFILE` of at
  least `1024`.
- Windows binaries are not code-signed and may show an unknown-publisher
  warning.

## Release acceptance

Do not publish the candidate until the exact release commit has passed:

- workspace formatting, warning-denied Clippy, MSRV checks, and the complete
  standard and feature-gated Rust test matrix;
- wallet typechecking, all frontend tests, and a production frontend build;
- Windows and Linux wallet and node builds;
- Windows and Linux CUDA/OpenCL standalone-miner packaging, backend inspection,
  and available-device differential smoke tests;
- binary version checks, archive extraction, launcher inspection, and a final
  independently verified SHA-256 manifest.

## Production status

Production activation remains fail-closed. The component and bounded
composition checks do not replace an unchanged full-size run. Mainnet still
requires the final model artifact and commitments, one exact n=33 end-to-end
proof with proof size, proving time, verification time, peak memory and disk
recorded, independent transcript and soundness review, adversarial public
testing, reproducible signed releases, and external security audit.

The Type-6 and Completed-transcript paths have bounded component coverage, but
have not completed cross-platform, operator-scale, or full production rehearsal.
This release does not claim a real production ceremony, external signature
collection, bulletin publication, independent mirror verification, or external
security review.
